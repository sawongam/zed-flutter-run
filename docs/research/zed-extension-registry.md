## 0. Blocking policy: no autonomous agents [verified-source]

`zed-industries/extensions/AI_POLICY.md`: AI-assisted coding is welcome, but "Autonomous agents are not allowed to be used for contributing to this project", PR body and replies to maintainers must be written by the human (AI context only in quote blocks with human commentary). Consequence: the submission PR and all review conversation must be done by a human maintainer of this project, not by an agent. Also CONTRIBUTING.md: untested extensions get closed without feedback ("Test your extension locally as a dev extension before submitting").

## 1. How submission works

Sources: `extensions/CONTRIBUTING.md`, `README.md`, `.github/workflows/ci.yml`, `src/package-extensions.js`, `src/lib/validation.js`; `zed/docs/src/extensions/publishing/{prerequisites,publishing-guide,updating-and-maintenance,faq,license-requirements}.md`.

- Mechanism [verified-source]: PR against `zed-industries/extensions` that (a) adds a git submodule at `extensions/{extension-id}` (HTTPS URL, public repo, commit must be on a branch, not detached) and (b) adds an entry to top-level `extensions.toml`:
  ```toml
  [my-extension]
  submodule = "extensions/my-extension"
  path = "packages/zed"   # optional, if extension.toml is in a subdirectory
  version = "0.0.1"       # must equal extension.toml version at that commit
  ```
  then run `pnpm sort-extensions` (sorts `extensions.toml` and `.gitmodules`; CI fails if unsorted).
- Update = bump submodule to new commit + bump `version` in `extensions.toml` (`git submodule update --remote extensions/<id>`). A community action exists: https://github.com/huacnlee/zed-extension-action. Same PR rules apply.
- PR rules [verified-source] (publishing-guide.md): exactly one extension per PR; max 3 open PRs per person; reply to maintainer feedback within 3 weeks or the PR is closed as stale (fresh PR allowed). Fork to a personal account (not an org) so staff can push to the PR.
- CI checks [verified-source] (`ci.yml`, `package-extensions.js`, `validation.js`, `dangerfile.ts`):
  1. `pnpm build`, `pnpm test`, then `pnpm package-extensions` which: checks `extensions.toml` valid (ids `^[a-z0-9\-]+$`, semver `major.minor.patch` only, submodule + version present), `.gitmodules` HTTPS, submodule name/path equals `extensions/<id>`; requires `id` in `extension.toml` equals the `extensions.toml` key; rejects legacy `extension.json`; runs license validation; builds with the pinned `zed-extension` CLI (Rust 1.90, target `wasm32-wasip2`); checks built manifest version equals `extensions.toml` version; checks `name` rules (see section 3).
  2. Sorted `extensions.toml`/`.gitmodules` check; no Git LFS in submodules.
  3. Danger: PR must modify `extensions.toml` (unless maintainer label `allow-no-extension`).
- Review [verified-source] (faq.md): human maintainer review, first feedback typically "within a few weeks", up to 1-2 months; PRs that severely violate prerequisites are closed without feedback. Not every submission is accepted. Prerequisites also forbid: duplicating functionality already in the registry (contribute to the existing extension first), misusing the API to work around limits, reading/modifying anything outside the extension's designated environment, non-English user-facing text.

## 2. License [verified-source]

BSD-3-Clause IS accepted. `publishing/license-requirements.md` (in force since 2025-10-01) lists: Apache 2.0, BSD 2-Clause, BSD 3-Clause, CC BY 4.0, GNU GPLv3, GNU LGPLv3, MIT, Unlicense, zlib. CI enforcement: `src/lib/license.js` (`isBsd3ClauseLicense`, template-text pattern matching, whitespace-normalised) and `src/lib/validation.js` `validateLicense`. Details:
- Any file whose name starts with `LICENSE`/`LICENCE` (case-insensitive, extension ignored) at the root of the *extension directory* (the `path` subdirectory if used; a repo-root license does not count for a subdirectory extension, a symlink is OK) is inspected.
- Matching is by required text patterns, so use the unmodified standard BSD-3 text (the BSD patterns require "Copyright", the two redistribution conditions, the standard disclaimer; a third clause variant is handled; also an "alternative" test fixture exists). Do not add custom clauses or a header that breaks the patterns.
- The requirement applies only to the extension code, not to downloaded tools; the downloaded Dart proxy/CLI may use any license (it is not compiled into the extension). If the Rust extension lives in the same repo as the Dart CLI under a different license, keep the extension in a subdirectory with its own accepted LICENSE.

## 3. Naming rules

Sources: `prerequisites.md`, `src/lib/validation.js`.
- Extension ID [verified-source]: unique, kebab-case, `^[a-z0-9\-]+$`, must not contain "zed" or "extension" (CI enforces: no `zed-` prefix, no `-zed` suffix, no substring `extension`; the prose says not to include `zed` at all), and must indicate what it provides. Existing ids are frozen, so older violations exist.
- Debugger-only extension [verified-source] (prerequisites.md "Debugger Extensions"): "make sure your extension ID reflects that (e.g., by suffixing it with `-debugger`)". Not CI-enforced in code I read, but a reviewer will ask. Also: "Do not bundle the debug adapter with the extension. Download it or check for it in the user's environment."
- Name (`name` in extension.toml) [verified-source]: must not start with "Zed ", end with " Zed", or contain "extension" (case-insensitive).
- Taken ids in `extensions.toml` at HEAD (2026-11-02) [verified-source, grep `^\[id\]`]: `flutter`, `flutter-debug`, `flutter-run-debug`, `flutter-debugger`, `flutter-dap` are all FREE. Closest existing ids: `dart` (zed-extensions/dart, v0.4.1, has debug adapter `Dart` and Flutter support), `flutter-snippets`, `freezed-dart-flutter-snippets`, `riverpod-dart-flutter-snippets`, debug ones `bugstalker-dap`, `unity-debugger`. No existing id ending `-debug`/`-dap`/`-debugger` refers to Flutter.
- Recommendation: `flutter-debugger` (follows the `-debugger` suffix guidance; plain `flutter` would claim the language-level namespace and invite "overlaps with dart" rejection; `flutter-debug`/`flutter-run-debug` do not match the suggested suffix). Display name e.g. "Flutter Debugger" (no "Zed", no "extension"). [verified-source for the rules, recommendation is a judgement]
- Adapter name uniqueness [unverified]: adapter names (`[debug_adapters.X]`) share a global namespace in Zed's debug.json `adapter` field; the official Dart extension uses `Dart`. Pick a different name (for example `Flutter` or `FlutterProxy`) to avoid ambiguity. I did not find a registry-level uniqueness check on adapter names in `validation.js`.

## 4. Binary downloads

Sources: `zed/docs/src/extensions/{capabilities,debugger-extensions}.md`, `zed/crates/extension_api/wit/since_v0.8.0/{extension,github}.wit`, `zed/crates/extension_host/src/wasm_host/wit/since_v0_8_0.rs`, `zed/crates/extension_host/src/capability_granter.rs`, `zed/crates/extension/src/extension_manifest.rs`.

- Policy [verified-source]: downloading the debug adapter from an external source (GitHub Releases, npm...) is the explicitly recommended pattern ("If you need to download the DAP server from an external source ... you can also do that in this function. Make sure to check for updates only periodically, as this function is called whenever a user spawns a new debug session"). Bundling the adapter inside the extension is forbidden. Downloading from our own GitHub Releases is therefore fine; the license rule does not cover downloaded tools.
- APIs [verified-source]: `latest_github_release(repo, GithubReleaseOptions{require_assets, pre_release})`, `github_release_by_tag_name(repo, tag)` (both return `GithubRelease{version, assets[]}` with `GithubReleaseAsset{name, download_url, digest}`); `download_file(url, path, DownloadedFileType::{Uncompressed|Gzip|GzipTar|Zip})` saves "within the extension's working directory"; `make_file_executable(path)` (no-op on Windows); `current_platform()` for os/arch.
- Capabilities [verified-source]:
  - The extension.toml `[[capabilities]]` table (kinds `process:exec`, `download_file`, `npm:install`) is used by the manifest check `allow_exec` (extension_manifest.rs). `process:exec` calls by the extension must be declared there, e.g. `kind="process:exec", command="...", args=["**"]` (example: unity-debugger).
  - For `download_file`, the code path (`since_v0_8_0.rs` `download_file`) only calls `capability_granter.grant_download_file(url)`, which checks the *user's* `granted_extension_capabilities` setting (default allows host `*`; users may restrict to e.g. `github.com`). I found no check of a manifest-declared `download_file` capability there. Existing registry extensions that download (php, emmylua) declare no `[[capabilities]]` at all. So: declare nothing for `download_file`, but declaring `{ kind = "download_file", host = "github.com", path = ["<owner>", "<repo>", "**"] }` is harmless and documents intent (docs/capabilities.md example). Whether a future host enforces manifest-level download capabilities is [unverified].
  - Returning a downloaded path as `DebugAdapterBinary.command` is executed by Zed itself, not through the extension's `process::Command`, so `process:exec` is not needed for it. emmylua and php declare none. [verified-source for those extensions; the general claim is an inference]
- Checksums: [verified-source] `download_file` performs NO hash verification (it just streams the HTTP body; HTTPS only protects transport). The GitHub release asset struct exposes `digest: Option<String>` ("SHA-256 of the release asset if provided by the GitHub API") but only in the `since_v0.8.0` WIT in Zed main. `zed_extension_api` 0.7.0 on crates.io (latest published when I queried, 2025-09-12; static.crates.io tarball) has no `digest` field. So with the published crate we must verify ourselves, and even with 0.8.0 the check is ours to do after download. Options: (a) read `digest` once an API version with it ships and compare; (b) vendor a pure-Rust `sha2` crate (compiles to wasm32-wasip2) and hash the file read via `std::fs` after `download_file(..., Uncompressed)`, comparing with a `SHA256SUMS`/per-asset `.sha256` fetched via `download_file` into the work dir (HTTP bodies cannot be read directly; download then `std::fs::read_to_string`). No sha256 host helper exists in the WIT. [verified-source for no helper: the extension.wit/github.wit I read; the vendoring plan is [unverified], untried]. Download as `Uncompressed` for the hash check, then extract/chmod; or hash the archive downloaded uncompressed, then unpack with host code is not available, so prefer shipping a bare per-platform executable asset (or the Dart AOT binary) as `Uncompressed` and `make_file_executable` it.
- Working directory [verified-source]: host work dir is `<extensions work_dir>/<extension-id>/` (`wasm_host.rs`: `self.work_dir.join(manifest.id)`); the WASM process's cwd is that directory; `download_file`'s path is resolved by `writeable_path_from_extension`, which rejects path escapes (tests `test_writeable_path_rejects_escape_attempts`). Extensions use relative paths (`std::fs`, `std::env::current_dir()`) there. Typical layout: `<dir>/<tool>-<version>/<binary>`, delete older version dirs after a successful new download (emmylua: `fs::read_dir(".")` cleanup; php: `Xdebug/Xdebug_<ver>`). The extension is re-instantiated across Zed restarts, so cache in a struct field and fall back to the highest installed version offline (php xdebug.rs does exactly this). Do not touch anything outside this dir (prerequisite).
- Rust/WASM caveats [verified-source, developing-extensions.md]: no `cfg` for platform and no `std::env::var`; use `current_platform()` and `Worktree` methods (`which`, `shell_env`, `root_path`).

## 5. Existing debug-adapter extensions that download a binary

None of the pure debug-only registry extensions I opened downloads a binary (unity-debugger, bugstalker-dap take a user-provided path / PATH). Closest working patterns [verified-source, cloned and read]:
1. EmmyLua, registry id `emmylua`, https://github.com/EmmyLuaLs/Zed-EmmyLua (MIT). `extension.toml`: `[debug_adapters.emmylua_new]` with `schema_path = "debug_adapter_schemas/emmylua_new.json"`, `[debug_locators.lua]`, no `[[capabilities]]`. `src/emmylua.rs` `get_dap_binary`: honors a user-provided path, then a cached path (`fs::metadata`), else `latest_github_release("EmmyLuaLs/emmylua_dap", {require_assets:true, pre_release:false})`, builds an asset name from `current_platform()` (`emmylua_dap-{darwin|linux|win32}-{x64|arm64|aarch64}...{tar.gz|zip}`), `download_file(url, "emmylua_dap-<ver>", GzipTar|Zip)`, removes old `emmylua_dap-*` dirs, returns `DebugAdapterBinary{command: Some(abs path from env::current_dir()), connection: None (stdio), ...}`. This is the closest model for our proxy (native binary over stdio). It also ships a language server, so it is a language+debug extension, not debug-only.
2. PHP, registry id `php`, https://github.com/zed-extensions/php (Zed's own, Apache-2.0). `extension.toml`: `[debug_adapters.Xdebug]` (default schema path `debug_adapter_schemas/Xdebug.json`), no capabilities. `src/xdebug.rs`: `latest_github_release("xdebug/vscode-php-debug")`, picks asset `php-debug-<ver>.vsix`, `download_file(.., "Xdebug/Xdebug_<ver>", Zip)` once per session (`OnceLock` version cache), offline fallback = highest local `Xdebug_*` dir, then runs it with `node_binary_path()` and a TCP connection via `resolve_tcp_template`. Good reference for the check-once-per-session and offline-fallback logic.
3. Dart, registry id `dart`, https://github.com/zed-extensions/dart (Apache-2.0). `extension.toml`: `[debug_adapters.Dart]` plus `[language_servers.dart]` and a grammar; `src/dart.rs` `get_dap_binary` / `dap_request_kind` find `dart`/`flutter` on PATH via `worktree.which` (no download). Relevant because it is the incumbent Flutter debug path: its schema `debug_adapter_schemas/Dart.json` supports `type: flutter`.
Debug-only without download (for the manifest shape only): `unity-debugger` (https://github.com/tomires/zed-unity-debugger: `[debug_adapters.unity]` + `schema_path` + `process:exec` capabilities, no language) and `bugstalker-dap` (https://github.com/godzie44/BugStalker, `extension/zed/extension.toml`: `[debug_adapters.bugstalker-dap]`, extension in a subdirectory via `path`). Other repos using `latest_github_release` in `get_dap_binary` (found by code search, not checked for registry membership/behavior): lucasmengarda/zed-bun-debugger, haytham818/netcoredbg-dap, slimfy1/cortex-debug-zed, Jarrio/Zed-Haxe-Debug [unverified].

Required pieces for any debug adapter [verified-source, debugger-extensions.md]: `[debug_adapters.NAME]` in extension.toml; a JSON schema (mandatory, default path `debug_adapter_schemas/NAME.json`); Rust `get_dap_binary` and `dap_request_kind`; strongly recommended `dap_config_to_scenario`; optional `[debug_locators.X]` with `dap_locator_create_scenario`/`run_dap_locator`. A Rust crate (`crate-type = "cdylib"`, `zed_extension_api`) is required for debuggers.

## 6. Debug adapter only, and coexistence with the Dart extension

- Debug-adapter-only extensions are allowed [verified-source]: prerequisites.md has a "Debugger Extensions" section (only requirement: id reflects it, e.g. `-debugger`); registry examples `unity-debugger` and `bugstalker-dap` have no language/grammar. The "Language Extensions" rules (grammar, similar id) apply only if you add a language, which we should not (do not redefine Dart or Flutter languages; "grammar reuse" is forbidden anyway per FAQ).
- Coexistence/dependency [verified-source for no dependency mechanism]: `ExtensionManifest` (extension_manifest.rs) has no `dependencies` field, and nothing in the registry CI links extensions. Two extensions may both be installed; they just register different adapters (`Dart` vs ours). We can only rely on the Dart extension's *language* (tree-sitter/LSP) being installed by the user, not enforce it. Note: Zed's debug UI picks adapters by name from `.zed/debug.json`; an extension cannot extend another's adapter. Document in README that the user also installs "Dart".
- Reviewer risk [verified-source policy, my interpretation]: prerequisites say "Publish functionality that is not already available in the extension registry" and FAQ prefers contributing to the existing extension. The official Dart extension already has a Flutter debug adapter, and the closed PRs (`zed-extensions/dart#72`, `zed-industries/zed#51873`) show maintainers reject toolbar-style Flutter-only changes. Our justification must be concrete (hot reload/restart, device selection, proxy features not feasible in the Dart extension) and written by a human in the PR body. [unverified how maintainers will weigh it]

## 7. Checklist for our future submission

Prepare in our repo:
- [ ] Extension directory (e.g. `zed-extension/`) with its own accepted `LICENSE` (BSD-3-Clause, unmodified standard text, file name starting `LICENSE`) at that directory root (symlink allowed); Cargo.toml `crate-type=["cdylib"]`, latest published `zed_extension_api` (0.7.0 when checked; digest field not yet published).
- [ ] `extension.toml`: `id = "flutter-debugger"` (free), `name = "Flutter Debugger"` (no "Zed"/"extension"), `schema_version = 1`, `version`, `authors`, `description`, `repository`; `[debug_adapters.<Name>]` with `schema_path`; no `[language_servers]`/grammar; optional `[[capabilities]]` download_file for `github.com/<owner>/<repo>/**`.
- [ ] `debug_adapter_schemas/<Name>.json` (mandatory) describing launch/attach config.
- [ ] Rust: `get_dap_binary` (user path override, then cached path, then `github_release_by_tag_name` for the version pinned to the extension version, or `latest_github_release`; asset chosen by `current_platform()`; `download_file` into `<tool>-<version>/`; `make_file_executable`; delete old version dirs; offline fallback to highest installed; check for updates once per session), `dap_request_kind`, `dap_config_to_scenario`. No bundled binary.
- [ ] Integrity: verify SHA-256 ourselves (vendor `sha2`, compare with published `SHA256SUMS` or the API `digest` once available); publish checksums in release assets. [unverified feasibility in WASM]
- [ ] Test as a dev extension in Zed (Install Dev Extension) at the exact commit to be submitted; `cargo build --target wasm32-wasip2` with Rust 1.90 to mirror CI.
- [ ] Release assets for linux/mac/windows x64+arm64 exist on a public GitHub Release before submission; the extension version matches the tool release.
Submission PR (by a human, not an agent):
- [ ] Fork `zed-industries/extensions` to a personal account; `git submodule add https://github.com/<owner>/<repo>.git extensions/flutter-debugger`; make sure the pinned commit is on a branch.
- [ ] Add to `extensions.toml`: `[flutter-debugger]`, `submodule = "extensions/flutter-debugger"`, `path = "<subdir>"` if applicable, `version = "x.y.z"` equal to `extension.toml`.
- [ ] `pnpm sort-extensions`; ensure no Git LFS in the repo.
- [ ] One extension per PR; reply to reviewers within 3 weeks; PR text in the human's own words; explain why this is not already covered by the `dart` extension.
- [ ] After merge, updates: bump submodule + version in `extensions.toml`.
