- **Reviewer:** independent architecture reviewer (did not write the plan). Date: 2026-11-03.
- **Scope:** simplicity, cross-platform correctness, failure modes, WP interface consistency, `zed_extension_api 0.7.0` correctness, whether the test plan proves Gate 5.

## Verified facts (so the author need not redo them)
- `cargo test` works on the host with `zed_extension_api 0.7.0`, with `crate-type = ["cdylib"]` only and an unguarded `register_extension!`. `cargo clippy --all-targets -D warnings` passes. [verified]

[verified: `wit/since_v0.6.0/*.wit`, `src/extension_api.rs:15-40,195-262`]
- Zed's default `granted_extension_capabilities` includes `download_file` for host `*`, path `**` (`assets/settings/default.json:2376-2378`). - Zed's `Session::shutdown` sends DAP `terminate` if `supports_terminate_request`, otherwise `disconnect`. Once that request completes it calls `adapter_client.kill()`, which kills the adapter process, i.e. our proxy (`crates/project/src/debugger/session.rs:2249-2300`, `crates/dap/src/client.rs:172-176`). [verified]

## Findings

### A1 - blocker - §4.8 tasks, §4.10 step 3, §6 WP7/WP8: the CLI half is unreachable for users who get the binary through the extension
**Problem.** `get_dap_binary` falls back to downloading the proxy into Zed's extension work dir. That is the default path for anyone who installs from the registry and does not already have `flutter_rd`. The generated tasks use `"command": "flutter_rd"` (§4.8) and `init`, `reload`, `restart`, `select-device` and `devtools` are all CLI commands run in a terminal. The downloaded binary is not on any PATH, so every task fails with "command not found". `init` itself cannot be run either. The error text promises `dart pub global activate flutter_rd`, but no WP or workflow publishes to pub.dev (`release.yml` only builds binaries). So the plan's "global users" story needs a manual install anyway, and that install is described nowhere as a required step. Hot reload, restart and device selection are the product, so this breaks the MVP flow. [reasoned from §4.8 and §4.10]
**Fix (pick one, record as an ADR).**
(a) Make "put `flutter_rd` on PATH" an explicit prerequisite. Publish to pub.dev in `release.yml` (or drop that sentence from the error), and document `dart pub global activate` plus release-binary install per OS.
(b) Also let the proxy tell the user where it is. On the first `launch` of a session, emit a `console` notice `[flutter_rd] CLI: <Platform.resolvedExecutable>` when the binary is not on PATH. Make `init` write the absolute path (`Platform.resolvedExecutable`) into `tasks.json` `command` when `flutter_rd` is not found on PATH. Only use this when `resolvedExecutable` is the AOT exe, not `dart`.
(c) Add a `[Hot Reload]`-less fallback so Zed's own `RerunSession` (DAP `restart`) always works with no CLI.
Without (a) or (b) the first-run experience is a broken task.

### A2 - major - §4.2 Shutdown, §5.4, §7: Zed's stop sequence is `terminate` then kill, not `disconnect`
**Problem.** The plan keys shutdown on a client `disconnect` (inject `terminate`, wait, forward `disconnect`). Real Zed sends `terminate` when the adapter advertises `supportsTerminateRequest`, and the Dart/Flutter DAP does. Immediately after the `terminate` response arrives Zed kills the proxy process (SIGKILL / TerminateProcess), so a `disconnect` normally never comes. [verified: `session.rs:2249-2300`, `client.rs:172`] Consequences:
- Step 2's `terminate`-injection logic is dead in the common path, and the "descendant sweep" (steps 1, 3-4) never runs because the proxy is killed right after forwarding the `terminate` response.
- The `flutter debug_adapter` handles `terminate` correctly itself (`app.stop`, then SIGTERM of its recorded pids) and then exits on stdin EOF, so the flutter_tester orphan from the spike is not expected here. But DDS or frontend_server stragglers, and everything in the attach case, are not guaranteed gone when the response is relayed.
- The session file is never deleted (SIGKILL), so every normal stop leaves a stale file for the next CLI call to prune. This is the common case, not an edge case.
**Fix.**
1. Treat client `terminate` as the primary shutdown trigger. Forward it (renumbered), and hold back the `terminate` response until: the adapter response arrived, the `terminated` event was seen (or 5 s passed), and the snapshotted descendants are gone (bounded wait + `terminateTree` on survivors). Delete the session file and stop the watcher/control server before relaying the response. Anything after the relay may never run.
2. Keep `disconnect` and stdin-EOF handling as secondary triggers.
3. Delete the session file as the first step of any shutdown so a SIGKILL right after leaves nothing stale.
4. `FakeDapClient` (WP10b) must mimic `Session::shutdown`: send `terminate`, wait for the response, then SIGKILL the proxy and assert no orphans and no session file. See A7.
5. Update §5.4 and spike finding 1 in the docs: in Zed the trigger is `terminate`.

### A3 - major - §4.10 step 3, open question 7: a PATH hit on a Windows `.bat` shim beats the pinned download and defeats cleanup
**Problem.** Resolution order is user setting, then `worktree.which("flutter_rd")`, then download. A `dart pub global activate` install on Windows creates `flutter_rd.bat` (`dart pub global run flutter_rd:flutter_rd %*`). `which` will return it. Zed then spawns the `.bat` as the DAP adapter: 1-2 s extra start, pub may print build messages, stdin/stdout pass through `cmd.exe` plus the Dart VM, and when Zed kills the "adapter" it kills `cmd.exe` only, so the real `dart.exe` proxy and its adapter tree survive (taskkill `/T` is not applied by Zed). That is the orphan problem on every Windows stop. [reasoned; shim contents and Zed's kill semantics on Windows: unverified]
**Fix.** On Windows ignore a `which` result ending in `.bat`/`.cmd` for the *adapter* binary (still fine for the user's terminal). Prefer the pinned download there, or require `dap.FlutterRD.binary`. Document: on Windows use the release `.exe`. Add a unit test for the selection function (`fn pick_command(user, which, os)` in the pure module).

### A4 - major - §4.3 matching/CLI behaviour: `reload`/`restart` act on sessions that cannot honour them
**Problem.** "Act on all matching sessions" includes (a) `kind: dart` sessions (Dart console debug in the same project): injected `hotReload` fails, so the whole command exits 4 even though the Flutter session reloaded; (b) `unresponsive` sessions (timeout kept the file): the CLI waits the full 120 s on a dead or port-reused listener and then exits 5; (c) sessions with `appStarted:false`: each yields exit 4 noise. The parent-directory match (`isWithin(D, projectRoot)`) in a monorepo reloads every app below D, which may be intended but should be said.
**Fix.** In `findSessionsFor`/commands: skip `kind != flutter` and `unresponsive` sessions with a one-line note (`skipped pid N: not a Flutter session`); report `appStarted:false` as `app not started yet` but count it as a warning, not a failure, if at least one other session succeeded. Exit 3 only if zero eligible sessions. Add these cases to WP2 acceptance.

### A5 - major - §4.6 watching strategy: the mitigation for inotify exhaustion does not mitigate it for Flutter projects
**Problem.** Planner concern 3 says it watches "each non-ignored top-level directory". For a Flutter project the top-level dirs are `lib`, `test`, `android`, `ios`, `macos`, `linux`, `windows`, `web`, `assets`, ... Only `build/`, `.dart_tool/`, `.git/`, `node_modules` are excluded. `DirectoryWatcher` is recursive and on Linux adds an inotify watch per subdirectory regardless of the event filter, so `ios/Pods`, `android/.gradle`, `android/app/build`, `macos/Pods`, `linux/flutter/ephemeral` are all watched. That is thousands of watches, which is exactly the failure the plan set out to avoid (default `max_user_watches` is often 8192 shared with Zed itself). [reasoned from `package:watcher` recursion; not measured]
**Fix (also simpler).** Use an allow-list instead of a deny-list. Watch `lib/`, `bin/`, `test/`, `integration_test/`, plus the static directory prefix of every `reloadOnSaveGlobs` entry (`assets/**.json` -> `assets/`), each only if it exists at arm time. That deletes the 5 s root rescan, the root-file poll and the hidden-directory logic for directories (events still need the hidden/ignored filter). A new top-level dir created later is out of scope for 0.1.0 (say so). Add a cap (for example 5 000 directories walked) with a warning notice and fallback to `lib/` only.

### A6 - major - §4.2 "State capture", §7.3, WP10b test 4: attach is an MVP requirement but its core behaviour is left to a test to "decide"
**Problem.** For attach the plan does not know: which event marks `appStarted`; whether `--no-dds` is required; which URI form (`ws://` vs `http://`) the adapter accepts; whether `toolArgs` is used for `flutter attach`. WP10b test 4 is half-written ("`--start-paused? no`", "`toolArgs: ["--no-dds"]`? the test decides"). The Flutter SDK and a runnable `flutter run --machine` are available to the planner, so these can be probed in ten minutes. Leaving them open means WP10a codes the arming logic blind, and WP10b has no precise acceptance criteria. [reasoned]
**Fix.** Run the probe before Gate 3 (launch `flutter run --machine -d flutter-tester`, then drive `flutter debug_adapter` with `request: attach` through the spike's fake client with `vmServiceUri` both ways). Write the answers into §4.2 and rewrite test 4 with exact steps and expected events. Also decide now whether `vmServiceInfoFile` (`--vmservice-out-file`) is the recommended attach mode.

### A7 - major - §7, WP9, WP10b: the test plan does not prove Gate 5 on Windows/macOS, nor Zed's real stop path
**Problem.** Gate 5 and the MVP list require Linux, macOS and Windows behaviour (`.bat`, paths, control channel not POSIX-only).
- All integration tests are Linux-only. WP3's real-process test is "POSIX only, skipped on Windows". So on Windows nothing spawns a real process, exercises `taskkill`, binds the loopback server, renames session files over a reader, or runs `buildProcessSpec` against a real `.bat`. Windows CI only runs pure functions plus `dart compile exe`. `dart_console_test` needs only the Dart SDK, so it could run on all three OSes.
- The harness tears down with DAP `disconnect` and asserts orphans after it (A2). It never exercises `terminate` then SIGKILL, which is what Zed does.
- Gate 5 names "terminate" for the Dart console fixture; test 1 covers natural exit and `disconnect`, not a `terminate` request.
- Missing failure-mode cases: adapter crash (kill the adapter mid-session), proxy stdin EOF, proxy SIGKILL then stale file pruned, two concurrent sessions in one project (one reload hits both), `reload` before `appStarted`, `reload` against a `kind: dart` session, a 1000-file change storm producing one reload (fake watcher is fine for the unit, but add one real-FS burst of ~200 writes).
- "Three bounded negative windows" is fine, but "`waitForNo(event, 3 s)`" negative checks on Windows/macOS file watchers are where latency differs most; no coverage exists there.
- CI `integration` job lists `flutter precache --linux?` with a question mark; flutter-tester must be present before the first 180 s wait. [reasoned]
**Fix.** (1) Run `dart_console_test` and a new no-Flutter `cli_e2e` subset (init, status, reload-no-session, stale prune) in the `dart` job on ubuntu, macos and windows (`dart test -t integration -n dart_console` style tags: `integration-dart`). (2) Add a Windows-runnable `ManagedProcess` test that spawns `cmd /c` or `dart` with a child and checks `terminateTree`. (3) Switch the FakeDapClient teardown to Zed's sequence and keep a second `disconnect` variant. (4) Add the missing failure-mode cases above to WP10b. (5) Pin `flutter precache --linux` (or equivalent) in the integration job.

### A8 - major - §6 interfaces: mismatches the WP agents will hit (WP10a cannot be built purely from the stated signatures)
1. **Status data vs `HotResult`.** The control `status` result needs `lastHotAction{command, reason, ok, at, durationMs}` and `hotActionInFlight` (§4.3). `HotResult` (WP1) has `ok, error, message, duration, coalesced` only: no `command`, `reason` or timestamp. `HotActions.last` therefore cannot feed it. Either add `command`, `reason`, `at` to `HotResult`, or drop `lastHotAction` (see A17, which removes the control `status` command).
2. **Own keys.** §4.2 step 1 says `flutterMode` and `platform` are removed, but `LaunchRewriter.ownKeys` (WP1) omits them. WP10a's `schema_test` rule (c) then expects them declared. Put both in one source of truth.
3. **Duplicate option.** §4.1 lists `--flutter-sdk` as a `dap` flag "besides global", yet `GlobalOptions.addTo` also adds `--flutter-sdk` to every command parser. `ArgParser.addOption` throws on a duplicate name, so `dap` would crash at startup. Remove it from the `dap` row.
4. **`DebuggerUris.isFirst`.** Prose says the first occurrence "also carries isFirst" but the class has no such field; WP10a needs it for `openDevToolsOnce`.
5. **`RequestInjector.inject` contract** is self-contradictory ("throws HotInjectException ... ? -> returns response; timeout => TimeoutException"). Specify: returns the response map including `success:false`; throws only `TimeoutException` and `StateError` on closed session; `HotActions` maps both.
6. **`InitTemplates`** in the schema_test text does not exist (the API is `debugScenarios`/`zedTasks`).
7. **`ProcessSpec`** is described with `runInShell:false` in §4.4 but the interface has no such field.
8. **Shared helpers WP agents may need but cannot add.** Rule 1 forbids touching `common/`. WP2 needs shared "no session" text, WP6 needs `Messages`, several need a flush-and-exit helper. WP0 must guess. Cheapest fix: drop the shared `Messages` class (A19) and let each module hold its own constants.
9. **Layout vs matrix.** §3 layout says `lib/flutter_rd.dart (barrel, WP10)`; the matrix says WP10a. Nobody owns `.gitignore`, the root `README.md`, `docs/MANUAL_ZED_TEST.md`/`RELEASE.md` (orchestrator, probably), or a version-sync check (see A20).

### A9 - minor - §4.2 HotActions, §4.6: save-reload vs busy/paused interplay loses reloads and raises false errors
**Problem.** (a) A save-triggered `reload()` while a manual `restart` is in flight returns `HotError.busy`; the coalescer treats a non-ok `ReloadOutcome` as a failed reload ("Hot reload failed: busy" notice) and does not retry, so the edit is never applied until the next save. (b) While the app is paused at a breakpoint the injected reload blocks (spike finding 4); at the 120 s timeout the user gets "Hot reload failed: timeout" although the reload is merely pending, and `busy` clears while the adapter is still reloading, so the next call overlaps. (c) Client-originated DAP `restart` (Zed's RerunSession) bypasses `HotActions` entirely, so it can overlap an injected reload.
**Fix.** Add `ReloadOutcome.busy` and have the coalescer set `pendingAfter` instead of reporting an error. Track `stopped`/`continued` events in `ProxyState` (`pausedThreads`); a save-triggered reload while paused is deferred with one notice ("paused; reload on resume") and runs on the next `continued`. Keep a timed-out injected request counted as in-flight until its late response arrives. Route a client `restart` through the same busy flag.

### A10 - minor - §4.2 Startup failure, adapter crash, stdio: failure surfaces are thin
**Problem.** (a) Adapter stderr: `ManagedProcess` exposes `stderr`, but nothing says it is drained; an undrained pipe can block the adapter. It is also the only place the Flutter tool reports things like "Waiting for another flutter command to release the startup lock" or SDK errors, and Zed shows adapter stderr only in a developer-only log view (zed-dap-client-behaviour Q8). (b) On unexpected adapter exit the proxy shuts down and exits, so Zed just sees EOF; no `terminated` event or explanatory `output` is sent. (c) A hung adapter before `initialize` (startup lock) only gets the 2 s startup-failure path for spawn errors, not for hangs. (d) Before `exit()` the proxy must `await stdout.flush()`; otherwise the last response/notice can be lost, especially on Windows pipes.
**Fix.** Drain adapter stderr into `Logger` and also mirror it as `output` (category `stderr`) until `launch` completes and again for the last ~20 lines on unexpected exit. On unexpected exit send `output` + `terminated` before closing. After 10 s without an `initialize` response emit a notice with the last stderr line. Flush before exit.

### A11 - minor - §4.3 listing/pruning: a stale file is only pruned when the connection is refused quickly
**Problem.** The ping uses a 2 s timeout and "timeout -> keep, unresponsive". On Windows a connect to a closed loopback port can take on the order of 1-2 s to fail, so a stale file may be classified "unresponsive" and kept forever, and N stale files cost N x 2 s if pinged serially. [unverified: Windows connect behaviour; well known for .NET and Winsock]. With A2, stale files are the normal result of every stop, so this path is hot.
**Fix.** Ping all files concurrently. Treat a *connect* timeout the same as refused (stale -> delete); apply the "keep" rule only when connect succeeded and no reply arrived. Delete the session file on every shutdown path (A2), so stale files only come from hard crashes.

### A12 - minor - §4.2 Shutdown steps 1/3, §4.12: process-tree handling is undefined on Windows and risks PID reuse
**Problem.** `snapshotDescendants` is specified via `ps` (POSIX); on Windows only `taskkill /T` is mentioned, so the "snapshot then kill survivors" logic has no Windows implementation, and `ps`/`/proc` fallbacks are unrelated to it. `wmic` is removed on recent Windows 11. Killing snapshot pids seconds later can hit a reused PID. The Flutter adapter already records `flutter_tools`' pid from `daemon.connected` (the code comment says the shell pid is unreliable on Windows), so that is the better Windows hook.
**Fix.** Define Windows `snapshotDescendants` as "adapter pid only" and make `terminateTree` use `taskkill /PID <adapter> /T /F`. On POSIX re-verify each snapshot pid's ppid chain or start time just before signalling (compare `ps -o lstart=`/`/proc/<pid>/stat` starttime), or skip pids whose parent is not 1 or an ancestor of the original tree.

### A13 - minor - §4.10 steps 3-4: download robustness and platform gaps
1. **macOS.** Files fetched by Zed's HTTP client are not quarantined, so Gatekeeper is not a problem for the extension path. A browser-downloaded release binary is quarantined and blocked ("cannot be verified"). Also confirm on a macOS runner that `dart compile exe` output is code-signed enough to run on arm64 after copying; CI only runs the binary it just built. [unverified] Add `codesign -dv` and a copy-then-run step to `ci.yml`, and document `xattr -d com.apple.quarantine`.
2. **Windows ARM64.** `current_platform()` returns `(Windows, Aarch64)` there and the plan errors. Map it to the `windows-x64` asset (runs under emulation) instead.
3. **Atomic install.** Download into `flutter_rd.part-<n>`, verify, then `std::fs::rename` into place; two Zed windows starting together otherwise write the same final path. When the file exists and the hash matches, still call `make_file_executable` (a crash between verify and chmod leaves a non-executable file that passes the hash check forever). Stale-directory deletion must ignore errors (Windows: old binary in use).
4. **Skip the GitHub API.** With pinned checksums the URL is deterministic: `https://github.com/saadbtch/run-and-debug-flutter/releases/download/v<ver>/<asset>`. `github_release_by_tag_name` adds an unauthenticated API call (60/h per IP), an extra failure mode and a dependency on the release being non-draft. Drop it.
5. **Paths.** `std::env::current_dir()?.join("flutter_rd-0.1.0/flutter_rd.exe")` yields mixed separators on Windows; probably fine for CreateProcess but [unverified]. Build the path with `Path` and test on Windows.
6. The `[[capabilities]]` block in `extension.toml` is documentation only; the grant comes from the user's Zed settings (default allows all). Keep it, but do not describe it as enforcement.

### A14 - minor - §4.10 "Pure core / thin glue", §6 WP8, Cargo.toml: the cfg split and `rlib` are unnecessary
**Problem.** Planner concern 4 doubts host linking. It works [verified, see top]. Hence `#[cfg(target_os = "wasi")]` around `glue.rs`/`register_extension!`, the `rlib` crate type and the "no zed types in pure modules" rule add nothing. Nine Rust files (`config`, `args`, `assets`, `checksum`, `checksums`, `locator`, `scenario`, `glue`, `lib`) for roughly 300 lines of logic is more than needed. `sha2 = "0.11"` needs hand-rolled hex (E0277 above).
**Fix.** Keep `crate-type = ["cdylib"]`; unit tests inside the modules run fine. Collapse to `lib.rs` (trait impl), `proxy_args.rs` (config + args + scenario), `install.rs` (asset naming + checksum + pin table), `locator.rs` (if kept, A15). Use `register_extension!` unguarded. Specify `fn hex(d: &[u8]) -> String` and a known-vector test. Remove the "if 0.11 fails use 0.10" hedge: 0.11 builds for wasm32-wasip2.

### A15 - minor - §4.10 locator, open question 8: defer, and fix the matcher if kept
**Problem.** The locator only works when the user sets `languages.Dart.debuggers`, which the extension cannot do, and it is not in the MVP list. If kept: Zed task `command` is commonly a whole shell line (`"command": "flutter run -d linux"` with no `args`). The matcher looks at `basename(command)` and `args`, so the most common spelling never matches.
**Fix.** Defer the locator to 0.2 (delete `locator.rs`, its WP8 tests, the `extension.toml` entry and the README mention). If kept, tokenize `command` on whitespace before matching and add that case to the tests.

### A16 - minor - §4.2 Sequence numbers: renumbering every request is more machinery than the problem needs
**Problem.** ADR 0004 §2 has the proxy renumber every client request and map `request_seq` back, with a bounded "late" set. Zed's counter starts at 1 and never approaches 1e9; the spike already proved a disjoint injected range (>= 1e9) works with zero collisions, and Zed never sends `cancel` (whose `requestId` would otherwise need rewriting) [verified]. Renumbering adds a map, a failure mode (unknown `request_seq` -> warning) and hot-path allocation.
**Fix (needs an ADR amendment).** Keep client seqs untouched; allocate injected requests from a separate counter starting at 1e9; swallow any response whose `request_seq` is in the injected set (a `Set<int>` plus the late set). Fail loudly (log + notice) if a client request ever carries seq >= 1e9. Delete `renumberClientRequest`, `Map<adapterSeq, clientSeq>` and their test matrix. If the orchestrator keeps ADR 0004, then at least add a note that `cancel.requestId` and `progressId` must be rewritten.

### A17 - minor - §4.3 control channel and session files: drop hardening that buys nothing
- **File name hash.** `<hash(projectRoot)>-<pid>.json` is never used, because the CLI reads every file and matches on contents. Use `<pid>.json`; removes `projectRootHash`, `sessionFileName(projectRoot, ...)` and the Windows-case hash test.
- **Per-file chmod / spawning `chmod`.** The sessions directory is `0700`; that alone protects the token. Drop the per-file `chmod 600` and the `ownerOnly` option on `atomicWriteString`. One directory chmod once at create.
- **Server hardening.** Binding to `loopbackIPv4` makes the "reject non-loopback remote address" check redundant. Cut it and the 8-connection cap. Keep token, line limit, idle timeout.
- **Control `status`.** Only the DevTools resolver (WP6) and `status` CLI use it, and the session file already holds device, mode, `vmServiceUri` and `appStarted`. Make `status` read session files plus `ping` (liveness). The control protocol shrinks to `ping`, `reload`, `restart`, and the `HotResult` gap (A8.1) disappears.
- **Rename retry.** 5 x 20 ms is short for a Windows sharing violation under AV; use 10 x 50 ms.

### A18 - minor - §4.7 DevTools: cut the fallback server and the second URL style
**Problem.** The planner's own probe shows DDS serves DevTools, `app.devTools` is emitted, and every page URL returns the same SPA. The plan still builds a probe, a `dart devtools --machine` fallback process with stay-alive semantics (`DartDevToolsServer`, `serverStarter` seam, `parseServerStarted`), `PageStyle.query`, `--no-probe` and `--session`. A fallback that keeps a CLI process alive in a hide-on-success task terminal is also awkward.
**Fix.** 0.1.0: build the DDS URL from the session file's `vmServiceUri` (path style), open it, print it with `--print`, otherwise error with the URL. Drop probe, fallback server, `PageStyle.query`, `--no-probe`, `--session`. Revisit if the manual browser check (MANUAL_ZED_TEST) fails. Roughly 40% of WP6 goes away.

### A19 - minor - scope and process overhead that can go without losing MVP
- `emulators` ("should") and `doctor --json` ("may"), `version --json`: cut; none are in the HANDOFF MVP list.
- `init --worktree` and relative-path templating (open question 6): cut for 0.1.0; keep the bidirectional `isWithin` match (cheap) and `--project`.
- Per-module `strings.dart` (8 files) plus `Messages`: for an English-only tool this is ceremony and it forces WP0 to guess shared text (A8.8). Allow `static const` strings in the file that uses them; keep the "no `print`" rule.

## Answers to the requested focus areas
1. **Simplicity.** See A14, A16, A17, A18, A19, A5. The three biggest cuts are renumbering (A16), the DevTools fallback (A18) and the per-top-level-dir watcher with rescan (A5).
2. **Cross-platform.** Windows: A3 (.bat shim), A7 (no real-process tests), A11 (connect timeout), A12 (tree snapshot), A13.2/13.5. macOS: A13.1 (codesign/quarantine, unverified), file-name casing is handled by `pathKey`. Linux: A5 (inotify). GUI PATH is handled by `shell_env()` for the proxy but not for tasks (A1).
3. **Failure modes.** A2 (Zed's real stop sequence), A9 (busy/paused/storm), A10 (adapter crash/stderr/flush), A11 (stale files), A4 (concurrent sessions). A `git checkout` storm is correctly coalesced by the debounce plus `pendingAfter`; the cost is one reload of a possibly half-checked-out tree, so consider a minimum 500 ms debounce for bursts of more than 20 files.
4. **Interface consistency.** A8. File ownership is disjoint as stated; there are no overlaps, only unowned files (A8.9, A20).
5. **Extension API.** Types match the crate (see verified facts). Corrections: A13.3/13.4 (download flow), A14 (host test feasible, `sha2` hex), A15 (locator input shape). `sha2 0.11` compiles for `wasm32-wasip2`.
6. **Gate 5.** A7: Linux integration proves launch, breakpoint, reload, restart, save-reload, stop-with-no-orphans and `init`/`devices`. It does not prove Windows/macOS process handling or the Zed `terminate` path.
