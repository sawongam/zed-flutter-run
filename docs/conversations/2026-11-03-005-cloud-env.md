## Headless Flutter target
Tried in the HANDOFF §2 order:
1. **`flutter-tester` works.** `flutter run --machine -d flutter-tester --show-test-device` in a fresh `flutter create` app produced `daemon.connected`, `app.start` (`supportsRestart: true`, `mode: debug`), `app.debugPort` (wsUri), `app.devTools` (a full DevTools URL with `?uri=`), `app.dtd`, `app.progress`, `app.started`. This is the target for integration tests.
2. `web-server` and 3. Linux desktop under `xvfb-run`: not needed as the primary target. GTK dev libs are installed so the Linux desktop target is available as a secondary check.

Note: `flutter-tester` only appears in device lists with `--show-test-device`. When the proxy drives `flutter debug_adapter`, the test passes `toolArgs: ["-d", "flutter-tester", "--show-test-device"]`.

## Blocked / workarounds
- Editing `~/.bashrc` to add the SDK to PATH was refused by the sandbox policy; symlinks in `/usr/local/bin` are used instead.
- `www.google-analytics.com` is blocked by the egress proxy (expected; analytics are off).
- Zed's GUI can't run here. Everything Zed-side is verified by reading Zed's source, and by a fake DAP client that sends exactly what Zed sends (see research/zed-dap-client-behaviour.md). The real-Zed steps go in `docs/MANUAL_ZED_TEST.md`.
